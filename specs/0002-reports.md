# 0002 — Markdown and HTML reports

| | |
|---|---|
| **Status** | Draft |
| **Threat model layer** | Layer 5 — Audit trail. A finding nobody can circulate is a finding nobody acts on. |
| **Breaking** | No. New flag; `--json` and terminal output unchanged. |

## Problem

The tool produces two outputs: a terminal stream for a human at a keyboard, and
`--json` for a machine. Neither survives the journey to where decisions get
made.

Pasting terminal output into a pull request or a chat channel loses the colour
that carried some of the hierarchy, keeps the phase noise, and arrives as a wall
of monospace nobody reads. Pasting JSON is worse. So the practical outcome today
is that a finding stays on the machine that found it, which is the wrong place
for anything that needs another person to act.

There is also a gap in the middle of the existing pair. `--json` is designed for
programmatic consumption — it is a flat findings array with counts. It is a poor
input to an LLM asked "what should I fix first and why", because it carries no
remediation text, no threat-model context, and no grouping.

## Goals

- A single file that can be attached to a PR, pasted into a chat channel, or
  read by an agent, and is legible in all three.
- Findings grouped by subsystem with remediation inline, so the reader does not
  need the tool to interpret them.
- Deterministic output for identical input, so two reports can be diffed.

## Non-goals

- **Replacing `--json`.** That contract stands for dashboards and alerting.
  This is a sibling, not a successor.
- **Uploading anywhere.** The tool writes a file. Posting it to Slack or a PR is
  the caller's business, and a security tool that makes outbound requests of its
  own accord is a worse tool.
- **Trend analysis across runs.** The SHA log already carries history and
  [0004](0004-rule-catalog.md) will give findings stable IDs; a report that
  compares two runs is a later spec, if ever.
- **PDF.** No.

## Design

### Flag

```
--report[=FORMAT]        write a report; FORMAT is markdown (default) or html
--report-out PATH        where to write it (default: alongside the log file)
```

`--report` with no format writes markdown. The default path is
`${LOG_DIR}/<same-timestamp>.md`, so a report sits next to the log it was
derived from and the pairing is obvious months later.

`--report-out -` writes to stdout. In that mode the human stream moves to
stderr, matching how `--json` already behaves — one output owns stdout at a
time.

### Markdown shape

Written for a human skimming a PR comment, which means the verdict is first and
the reader can stop after it.

```markdown
# update-toolchain — ACTION REQUIRED

`dry-run` on `hostname` · macOS 26.1 arm64 · 2026-08-25T03:48Z · 3m 12s

**12 findings across 4 subsystems** — 3 error, 9 warning.
9 have a documented remediation.

| Severity | Check | Subject | Remediation |
|---|---|---|---|
| error | `mcp.secret-plaintext` | `deploy-api` / `DEPLOY_API_TOKEN` | Move to keychain, reference as `${VAR}` |
| error | `mcp.tls-disabled` | `deploy-api` | Remove `NODE_TLS_REJECT_UNAUTHORIZED=0` |

## Agent configuration

### `mcp.secret-plaintext` — error

A 191-character literal is stored as `DEPLOY_API_TOKEN` in
`~/.kiro/settings/mcp.json`. Any process able to read that file can read the
credential, and the file is routinely committed to dotfile repositories.

**Fix:** store the value in the system keychain and reference it as
`${DEPLOY_API_TOKEN}` in the config.

**Threat:** SECURITY.md Layer 3 — Source allowlisting.
[MCP security: local server compromise](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices)

<details><summary>10 passing checks</summary>

- homebrew remote origin verified
- 10/10 taps trusted
…
</details>
```

Passing checks go in a collapsed `<details>` block. Present for completeness,
absent from the reader's first pass. GitHub, GitLab, and most chat renderers
handle `<details>` in markdown; renderers that don't will show the contents
inline, which degrades to merely verbose rather than broken.

Secret **values** never appear. Length and key name only. This is not
negotiable: the tool would otherwise be a mechanism for copying credentials into
a pull request.

### HTML shape

The same content, self-contained: inline CSS, no external fonts, no JavaScript,
no network requests when opened. Intended for archiving a run or attaching to a
ticket that renders HTML but not markdown.

Generated by wrapping the markdown body in a minimal shell rather than by a
second templating pass — one content generator, two envelopes. A markdown-to-HTML
conversion in bash is not worth writing, so the HTML path emits HTML directly
from the same finding loop, sharing the data and not the formatting.

### Why this is also the agent-facing format

An LLM asked to triage a run gets more from the markdown than from the JSON,
because the markdown carries what the JSON deliberately omits: remediation text,
threat-model citation, and grouping. `--report --report-out -` is therefore the
sensible thing to hand an agent, and [0005] (an MCP server, unwritten) would
serve this rather than the JSON.

Stated here because it changes a design decision: the remediation and threat
fields are not decoration for humans, they are the payload. They must be
populated for every rule, which is a requirement on
[0004](0004-rule-catalog.md), not on this spec.

### Determinism

Two runs finding the same things produce byte-identical reports apart from
timestamp, hostname, and duration. Findings are sorted by severity, then check
ID, then subject. No map iteration order leaks into output.

This makes `diff` between two reports meaningful, which is the cheap version of
trend analysis and the reason not to spec the expensive version.

## Acceptance criteria

1. `--report` writes a markdown file and the run's exit code is unaffected.
2. `--report=html` writes a file that opens in a browser with no network access
   and renders the same findings.
3. `--report --report-out -` writes the report to stdout and nothing else to
   stdout; progress goes to stderr.
4. `--report --json` is rejected with a clear error naming the conflict, since
   both would claim stdout when `--report-out -` is in play. When
   `--report-out` is a path, both are permitted.
5. No secret value appears in any report. A rule that detects a credential emits
   the key name and the value's length, never the value. Verified by a test that
   plants a known sentinel string in a fixture config and greps the report for
   it.
6. Two runs over identical inputs produce reports that differ only in timestamp,
   hostname, and duration fields.
7. Findings in the report are exactly the `[WARN]` and `[ERROR]` lines in the
   log — no more, no fewer.
8. A run with zero findings still produces a report, stating that, with the
   passing checks in the collapsed block. An empty report file is a bug.
9. The report renders without raw markup artefacts on GitHub. Checked by eye at
   review time; not automatable here.
10. Report generation adds under one second to a run.

## Constraints in play

**Read-only modes stay read-only.** `--dry` and `--audit` may write the report,
because the log directory is already the one place these modes write. Nothing
outside `${LOG_DIR}` is touched unless `--report-out` names it, which is an
explicit instruction from the caller.

**bash 3.2.** No associative arrays for the findings table. The report is
generated by re-reading the log file, the same source the summary and the JSON
already use, so no new data structure is introduced.

**Config is data, never code.** The report contains file paths and config key
names read from the user's agent configs. It is written, never evaluated. Worth
stating because a templating scheme that used `eval` to interpolate would
reintroduce exactly the hazard the config loader was built to avoid.

## Open questions

- Whether the markdown report should embed the SHA-diff section verbatim or
  summarise it. A run after a large `brew upgrade` can legitimately produce
  thirty SHA changes, which would dominate a PR comment. Leaning: summarise,
  with the full list in the collapsed block.
- Whether `--report` should imply anything about exit codes. Current answer: no,
  `--fail-on` is the only gate and reporting is orthogonal to it.
